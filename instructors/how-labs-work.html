How labs work: the mental model

The mental model, settings and routines every instructor needs before teaching on Skillable.

Audience
Instructors, SMEs and TAs delivering any GA program on Skillable
Time
10 min read

The mental model: images, not machines

A Skillable lab is not “a student’s computer in the cloud.” It’s a template.

  • GA builds and saves a VM image (the operating system, tools, settings) in Skillable Studio.
  • Every time a student launches a lab, Skillable creates a fresh copy of that image just for them. This is called a lab instance.
  • When the lab instance ends, the copy is deleted. The next launch is another fresh copy of the original image.

So by default:

Survives Does not survive
The original image GA built Files the student created
Anything pushed to GitHub Installed packages, config changes
The student’s TMS account and progress record Logged-in sessions (gh auth, API keys set in the shell, browser logins)

The one-line version for students: the machine is borrowed, your code is yours only once it’s on GitHub.

Ephemeral vs saved labs

Skillable supports two behaviors, set per lab by GA.

Ephemeral (end-only). The Exit menu shows only End. Closing the lab destroys the instance. The next session is a clean machine.

Saveable. The Exit menu shows Save and Close. The instance is paused and kept until a save expiry date shown to the student. Relaunching resumes where they left off and doesn’t count as a new launch.

Points to know about saved labs:

  • Saves expire. The student sees the expiry date when saving. Reopening and saving again pushes the date out.
  • Standard Skillable limits: students can hold 2 saved labs; instructors 5. Save periods for instructor-led classes are typically 7 days, and GA can ask Skillable for different periods.
  • Cancel is not Save. Cancel throws the work away.

Which behavior a lab uses is a program decision. Ask the program’s CSM.

Timeouts and limits

Every lab has settings GA configures in Studio. The timeouts below use Skillable’s defaults unless the delivery team asks for something different. They can be configured to whatever a program needs.

Setting What it does Value
Lab duration How long one launch can run Set per lab
Idle timeout Warns or disconnects after no activity Default: 15 minutes
Closed-window timeout Shuts the lab down after the lab window is closed Default: 60 minutes
Extension Student can add time when warned Set per lab
Launch limit How many times a lab can be launched Set per course
Access window When students can launch at all Class start through any post-class access period, set per program

What to do: at the start of each session, tell students how long the lab runs and remind them to respond to timeout warnings. A student who ignores the warning can lose an unsaved lab.

The save-your-work routine

Make this a ritual, not a reminder. Teach it on day one.

Start of session

git clone <repo-url>      # on a fresh machine
# or
git pull                  # on a resumed machine

Every natural break (lab step done, before lunch, before a demo)

git add .
git commit -m "describe what changed"
git push

End of session

  1. Commit and push.
  2. Confirm the commit is visible on GitHub in the browser.
  3. Then use the Exit menu.

Also redo each fresh session: sign in to GitHub CLI (gh auth login), re-set any API keys you added yourself (keys GA injects at launch are set automatically), and reinstall any extra packages that aren’t in the base image.

Never commit secrets. Keys go in environment variables or a .env file listed in .gitignore. More on this in the FAQ.

What happens if…

Situation Outcome What to tell the student
Closes the lab tab Instance keeps running (60 minutes by default) Relaunch from TMS to reconnect
Walks away Idle timeout warns, then shuts down Respond to the warning or push before stepping away
Power / Wi-Fi loss Treated as idle Reconnect fast; work since the last push is at risk
Clicks Cancel by mistake Work on the machine is gone Re-clone from GitHub
Lab timer runs out Lab ends Extend when warned; push regularly
Saved lab expires Saved instance is deleted Reopen and re-save before expiry

Skillable has some auto-save behavior when a lab has been inactive for a while, but it’s not something to rely on. It depends on lab settings and timing, and an active lab that simply runs out of time won’t auto-save. GitHub is the backup plan.
