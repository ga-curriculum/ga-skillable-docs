Writing lab instructions

Structure, step-writing and formatting conventions for GA labs, based on Skillable’s guidance.

Audience
LEDs and SMEs
Time
10 min read

Structure the lab

  • One task per page. End each page with ===, which creates a Next button. Short pages keep learners oriented and make “which step are you on?” easy to answer.
  • Start each page with a Heading 1 (#). Skillable shows it on the navigation buttons, as long as it is 40 characters or fewer.
  • Use Heading 2 (##) for tasks that share a page, and Heading 3 for tasks inside an exercise. If you need Heading 4, restructure.
  • Start every heading with a verb, in sentence case, with no full stop: “Create the API key”, not “API Key Creation.”
  • If a heading contains “and”, you may be combining two tasks. Split it.
  • Open each task with one sentence that says what the learner will achieve and why.

Write the steps

Where, what, why. Say where the learner is, then what to do, then why. Many learners stop reading after the first few words, so put the action first.

In the terminal, run the following command to install the project’s dependencies.

  • One sentence per step. Combine two short actions only if they’re part of the same task.
  • Be specific. Give exact names, values and messages. No “choose any name.”
  • Number the steps and add a check box, so learners can track progress: 1. [] step. Progress in TMS is the percentage of these boxes ticked.
  • Say “save your changes” rather than naming a button that might be renamed later.

Format consistently

  • Bold is only for things learners click or select, such as Save or File Explorer.
  • Don’t bold click-to-type or click-to-copy text. It already stands out.
  • Inside callouts, use italics rather than bold, and avoid quotation marks.
  • Use a table for settings learners must configure, and only list the ones that differ from the defaults.
  • Use screenshots sparingly, cropped to the part of the screen that matters.

GA conventions

These are the house rules for GA labs. A few deliberately differ from Skillable’s defaults.

Convention Why
Commands learners should learn go in code blocks, not click-to-type. Skillable suggests making everything clickable. For our programs, if everything is click-to-type, learners learn to click, not to code.
Use click-to-type for setup lines (paths, long URLs, one-off commands). It saves time on things that aren’t the point of the lesson.
Every page that ends a session has the save alert: commit, push, check GitHub. Lab machines are disposable. GitHub is the backup.
Spoilers and answers go in expandable hints ([+Hint]). Learners can try first, then reveal.
The lab instance ID is in a footer on every page. It’s the first thing anyone needs when a learner reports a problem.
Alert for anything that loses work. Knowledge for background. Hint for help. Learners learn what each color means.

The Markdown reference shows the syntax for each of these.

Watch the indentation

Most broken-looking labs come down to indentation.

  • An extra space before 1. turns the step into a second-level item.
  • A callout, image or code block between numbered steps must be indented under the step, or the numbering restarts.
  • Indent a table that sits inside a numbered step.
  • Limit callouts to one between steps (two at most), so the steps stay easy to follow.
