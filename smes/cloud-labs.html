How cloud access works

A Skillable lab can do more than run a machine. It can also launch against a cloud subscription. Azure and AWS are built in, and other platforms can be connected. The lab admin sets this up in Studio from your tech requirements:

  • Cloud resources can be created automatically for each learner when the lab launches, from a template.
  • Cloud sign-in details can be issued to each learner and shown in the lab instructions.
  • Shared resources can be created once for the whole cohort and used by everyone.

Shared or one per learner?

One per learner Shared by the cohort
Isolation Learners can’t affect each other One learner can change or delete things others use
Permissions Learners can safely have broad rights on their own resources Keep learners to the smallest role that works
Cost Multiplies by headcount One cost for the cohort
Capacity May hit cloud limits for large groups Rarely an issue

Say which you need for each service, and why, in the requirements.

Show sign-in details in the instructions

Cloud tokens fill in each learner’s own details when the lab launches. They only work in labs that use a cloud subscription.

Token Gives you
@lab.CloudPortalCredential(User1).Username The learner’s cloud portal username
@lab.CloudPortalCredential(User1).Password Their cloud portal password
@lab.CloudSubscription.Id The ID of the subscription the lab launched against
@lab.CloudSubscription.Name The subscription’s name
@lab.CloudSubscription.TenantName The tenant’s name
@lab.CloudResourceTemplate(Template1).Parameters[name] A value used to create the learner’s resources, such as a unique resource name

The exact names (User1, Template1) depend on how the lab is set up. Ask the lab admin which tokens your lab has.

Credentials and keys

Never share credentials in chat, on slides or in any unencrypted message. Ask for one of these instead, in this order:

  1. Issued at launch by Skillable, and shown with a token or set in the environment. Nothing to hand out, and nothing to leak.
  2. Written into the lab image before delivery, for example a .env file already in place in the starter code. Lab steps should only create a .env if one doesn’t exist, so they never overwrite it.
  3. Sent through a channel approved for credentials, if neither of the above is possible.

Keep them out of GitHub. .env always goes in .gitignore. Only an example file with empty values belongs in a repository. If a real key is ever pushed, treat it as compromised and rotate it.

Keep key-based sign-in turned on for services learners reach with a key. If it’s turned off, every learner needs their own cloud role and sign-in instead.

Network access

The lab machine can only reach the sites it’s allowed to. List every domain your labs need, for example:

  • Your Git host (for example github.com)
  • Package indexes (for example pypi.org and files.pythonhosted.org)
  • Every cloud service endpoint and portal
  • The sign-in service for the cloud platform
  • Any AI or other outside API the labs call

A blocked domain is the most common cause of failures on delivery day. The lab admin checks the list before the first session, so it has to be complete.

Cost and cleanup

  • Cloud services cost money while they exist, even if nobody is using them. Note anything billed by the hour, and anything multiplied by headcount.
  • Plan the cleanup in your requirements: which resources to delete, which keys to rotate, and which accounts and roles to remove when the program ends.
