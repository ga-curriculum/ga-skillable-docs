Write the tech requirements

The document the lab admin uses to build the lab image and any cloud services. If it’s not in here, it won’t be on the machine.

Audience
Subject matter experts
Time
8 min read

Use whatever format your team already uses. Just make sure it answers everything below. Send it to the lab admin with the lab instructions, at least 14 days before the first session. A new machine image needs at least 5 days of that, and cloud services can take 1 to 2 weeks. See lead times.

What to include

Section What to include Why it matters
Operating system and shell Windows or Linux, and the shell learners use (PowerShell, Bash) Decides the image, and the language tag on every code block
Languages Each language with a minimum and an expected version. Any command differences (for example python versus py) Learners copy commands exactly. One wrong command name stops a lab
Packages A full list with exact pinned versions, which sessions use each, and how they’re installed (globally, or in a virtual environment) Pinned versions mean every learner gets the same behavior. Unpinned ones change under you
Tools on the machine Editor, Git, command-line tools, AI tools and how each one signs in, required extensions Anything missing has to be installed by learners every fresh session
Not available Tools learners might expect that won’t be there, and what to use instead Saves instructors from live workarounds
Cloud services Each service, its type and tier, which labs use it, the region, and whether it’s shared or one per learner The lab admin provisions these. See Cloud services, access and credentials
Access and roles Who needs which role, on what, and why: learners, instructors and the setup account Too little access breaks a lab. Too much lets learners delete shared work
Network access Every outside domain the labs reach, and what needs it A blocked domain is the most common delivery-day failure
Credentials and environment variables Every key and variable: who needs it, which sessions, and how it reaches the machine Credentials must never be shared in chat or on slides
Session by session What each session needs that the one before didn’t Lets Lab admin and instructors check readiness day by day
Test status Which labs you’ve tested in a real Skillable launch, and which are untested Untested requirements are guesses. Mark them clearly
Open questions Anything undecided, with who decides Gets decisions made before the build, not during class
Costs What bills by the hour or per use, and how it scales with headcount Cloud services cost money even when nobody is using them
Cleanup What to delete, revoke or rotate when the program ends Stops costs and closes access once the program ends

Tips from past programs

  • Pin exact versions (==1.2.3, not >=1.2) for anything a lab depends on. Use ranges only where any recent version genuinely works.
  • Test in Skillable, not just on your own machine or in a plain cloud account. Images and network rules differ.
  • Test with a learner account. Admin and instructor accounts can do things learners can’t, which hides missing permissions.
  • Name roles exactly. Cloud providers rename roles. Give the role’s ID as well as its name.
  • Say what’s not used. If a lesson mentions a tool learners won’t install, list it, so nobody adds it to the image by mistake.
  • Keep the requirements with the course, and update them when a lab changes.
